# Rowan на живом ПК: список проверок и автоцикл

Владелец: «когда я прошу голосом что-то сделать, он не может — например открыть
Ютуб». Этот файл — очередь реальных проверок и то, что о них известно. Каждая
проверка выполняется **на живом ПК** через настоящую модель и настоящие
инструменты: `python scripts/live-eval.py --actions`.

Критерий готовности проверки: она PASS в отчёте `data/live-eval/last.json`
И причина, по которой она падала раньше, устранена в коде (а не подправлена в
самом тесте).

## Как это запускается

```powershell
pwsh -File run-eval.ps1              # автоцикл: прогон -> разбор -> правка -> прогон
pwsh -File run-eval.ps1 -Rounds 3    # не больше трёх кругов
python scripts/live-eval.py --actions --json data/live-eval/last.json
python scripts/live-eval.py --actions --scenario VE-01 --scenario VE-06
python scripts/live-eval.py --actions --dangerous   # + сценарии, которые реально спят/кликают
```

Проверки, помеченные `live_only`, автоцикл пропускает: они спят ПК, блокируют
сессию, отправляют настоящее сообщение или кликают по экрану.

### Оговорки к таблице (прогон 22.09 19:34, `data/live-eval/last.json`)

Строки VE-32 и VE-33 в прошлой версии файла были перепутаны: пометка
«спрашивает имя, не позвав инструмент» относится к VE-32 («запомни моё лицо»),
а VE-33 «это мой голос, сохрани» инструмент `enroll_voice` как раз зовёт.

Несколько PASS того прогона слабее, чем кажется: судья сценария ищет слова в
аргументах вызова целиком, включая служебное `purpose`, а `[x]` ставится и за
один правильный ответ:

- **VE-07/VE-08/VE-11** формально прошли, хотя `browser_control read` возвращал
  окно без документа (`url: ""`, `title: "Search icon"`, `elements: []`), а
  ответы были «страница не загрузилась». VE-08 зачёл слово «Videos» из
  `purpose`, VE-11 проверяет только имя инструмента.
- **VE-10** прошёл на честной ошибке `ok: false`: «Could not focus the browser
  page for scrolling» — страница не прокручена.

Поэтому сценарии семейства «читать страницу и действовать на ней» (VE-07…VE-11)
всё ещё требуют разбора: сначала надо понять, почему выбранное окно Chrome не
отдаёт документ, и заодно ужесточить судью, чтобы `purpose` не давал PASS.

## Что этот стенд не проверяет

Микрофон, wake word, диаризацию, голосовую идентификацию и звук динамиков:
стенд посылает текст как клиент с собственным VAD/STT (сообщение
`utterance_text`, ТЗ F-711). Это ровно та половина, где живут жалобы «прошу —
не может»: понимание и действия. Голосовую половину владелец проверяет сам,
говоря в комнату; её ошибки видны в `data/server.log` и в `/admin/turns`.

**Scripted-ходы хаба.** Стенд зовёт `hub.llm.LlmClient` напрямую, поэтому не
видит те ходы, которые живой хаб делает до модели: напоминания и будильник
(ТЗ F-417), регистрацию голоса и лица (F-2xx), выбор приложения
(`hub/app_choices.py`), `_clarification_turn`. Для сценариев, где хаб отвечает
сам, у сценария есть поле `hub_rule`: тогда стенд прогоняет настоящий ход хаба
(сейчас — `_reminder_turn`) на своей базе `data/live-eval/hub-rule.db`. Этим
ещё не закрыто: VE-32 (в живом хабе имя спрашивает сам хаб — видно в
`turn_events` 22.09 18:40, там же 0 вызовов инструментов) и VE-29 (в комнате
стенда нет умных устройств, и описание инструмента прямо запрещает звать
`set_light` при пустом списке — это верное поведение продукта, а не падение).
