# Jarvis: переход на OpenAI и постоянное восприятие комнаты

Статус: первый этап внедрён, инструкция — [OPENAI_SETUP.md](OPENAI_SETUP.md).
Реализованы текстовый API с учётом расходов, отдельный локальный vision URL,
строгий wake word, сигнал фоновой речи для задержки приветствий, прямые
команды ПК и отправка аудио между группами предложений. API-ключ отсутствовал
при разработке: доступность модели для аккаунта и реальные задержки пока не
проверены. Остальные пункты ниже остаются проектом, включая новый голос,
несколько камер и переработку узнавания людей. Контракт кода обновлён в SPEC.md.

## Цель

Естественный разговор с возможностью перебить ассистента, выполнение обычных
команд за секунды, несколько постоянно работающих камер, узнавание знакомых
людей и уместные приветствия. RTX 5090 используется для фонового восприятия
и локальных embeddings, распознавания речи и синтеза голоса. OpenAI получает
текст для разговора и решения задач. Уточнённое ограничение пользователя:
не более $20 в месяц на API, активация по wake word. Облачные голосовые
сессии исключены из базового варианта; ожидание не вызывает API.

## Что установлено в существующем проекте

- `server/llm.py` имеет OpenAI-совместимый Chat Completions backend, но запрос
  блокирующий, без потокового вывода, с общими `temperature` и `max_tokens`.
  Совместимость параметров нужно проверять для выбранной модели.
- `server/vision.py` независимо от провайдера обращается к Ollama `/api/chat`
  через тот же `llm.base_url`. Простая замена адреса на OpenAI сломает зрение.
- `server/app.py::_handle_utterance` последовательно ждёт STT, определение
  голоса, цикл LLM/tools, иногда дополнительный LLM self-check, затем TTS.
- `server/app.py::_stream_tts` ждёт синтеза всей реплики до отправки первого
  аудиофрейма. Передача чанками здесь не означает потоковую генерацию речи.
- `prompts/system.md` предписывает всегда отвечать по-английски, обычно одной
  фразой, в манере дворецкого. Поведение определяется и этими инструкциями.
- Камера задаётся одним целочисленным `client.camera.index`; для нескольких
  источников нужны идентификаторы камер и отдельные состояния присутствия.
- `server/session.py` хранит между репликами пары user/assistant; сведения
  о выполненных действиях следует сохранять отдельно в структурированном виде.
- Уже есть полезные исполнители устройств и ПК, HUD, память, профили людей,
  таймауты и тесты. Их можно сохранить при замене оркестратора.

В `data/server.log` найдено 229 завершённых реплик. В последних 30:
8 дольше 10 секунд, максимум 70.565 секунды; средние STT — 771 мс,
LLM — 10531 мс, TTS — 296 мс. Этап LLM включает инструменты и проверки,
поэтому эти числа не измеряют скорость генерации модели в отдельности.
Лог не учитывает полную пользовательскую задержку от конца речи до эффекта
на экране или первого звука. Это диагностическая выборка, не бенчмарк.

## Предлагаемое разделение

```text
Микрофон → локальный wake word → локальное распознавание речи
                                      ↓
                          Оркестратор на сервере
                         /                     \
             простая однозначная команда     текстовый OpenAI API
                         \                     /
                          исполнитель / ответ
                                      ↓
                          локальный синтез → динамики

Камеры → локальная обработка на 5090 → состояние комнаты и память
```

### Голос и понимание

Базовая архитектура после уточнения бюджета — локальные STT и TTS,
текстовый OpenAI Responses API между ними. Для качественного диалога и
инструментов кандидат для замера — GPT-5.4 mini; GPT-5.6 Luna — более дешёвый
кандидат для ограниченных задач после проверки успешности. Не добавлять
платный классификатор перед каждой репликой. Окончательный выбор требует
замеров качества и скорости на командах пользователя.

Whisper сначала проверить на записанных тестовых фразах: обрезание начала
после wake word, шум телевизора, выбор языка и качество входного аудио.
Отказ от большой постоянно загруженной локальной LLM освободит VRAM,
но одновременное размещение всех моделей всё равно нужно измерить.
Для нового локального голоса провести сравнение образцов и времени до первого
звука; сохранение нынешнего Silero не является требованием. Узнавание говорящего
проверяется отдельно от качества транскрипции.

Микрофон должен передавать речь по мере поступления. Нужны подавление эха
динамиков, корректное определение конца реплики, остановка воспроизведения
при перебивании и явная отмена дальнейших действий по команде «стоп».
Остановка речи и отмена действий — разные операции; уже выполненное действие
нельзя считать отменённым. Чанки и ответы маркируются session_id/turn_id,
запоздалые результаты старой реплики не озвучиваются и не запускают новые шаги.

Wake word остаётся локальным в ожидании. После ответа допускается короткое
локальное окно продолжения; тишина не создаёт API-запросов. Знакомое приветствие
можно проигрывать из локального аудиокэша, не вызывая облачную модель.
Перед внедрением нужно проверить микрофон на шуме телевизора и расстоянии:
новый API сам по себе не исправляет плохой аудиосигнал.

### Быстрые действия на ПК

Обычные операции — громкость, пауза, открытие приложения, URL, переключение
окна — получают прямые инструменты с проверяемым результатом. Использовать
существующий Dispatcher. Один определённый запрос должен вызывать минимум
сетевых раундов. Успех проверяет исполнитель; дополнительный LLM self-check
нужен по показаниям, а не после каждого изменения громкости.

Для интерфейсов порядок предпочтения: специальный API/инструмент,
Windows UI Automation или DOM браузера, затем скриншот и визуальный клик.
Последние два пути потребуют отдельных адаптеров. Зависимые действия остаются
последовательными. Повторы изменяющих состояние команд должны учитывать
operation_id, чтобы сетевой retry не выполнил их дважды.

### Несколько камер и люди

Добавить реестр камер: camera_id, room_id, тип источника, состояние соединения.
Захват имеет ограниченную очередь и обрабатывает свежий кадр; медленная модель
не должна создавать минутный хвост видео. Детектор и трекер работают постоянно,
распознавание лица — на качественных кадрах, SAM3 — по запросу поиска/сегментации.
SAM3 не является моделью идентификации человека.

Наблюдение: camera_id, track_id, captured_at, person_id либо unknown,
качество и уверенность. Общий сервис объединяет подтверждённые наблюдения
между камерами. Недоступная камера не доказывает, что человек ушёл.
Состояния: появился → подтверждён → присутствует → ушёл; события дедуплицируются.

Профиль человека: устойчивый person_id, имя, несколько проверенных образцов,
голосовой профиль и связанные факты. Имя связывается с профилем при знакомстве;
модель не угадывает имя по внешности. Слабый матч не обновляет эталонный профиль.
Голос — дополнительное свидетельство. Наличие одного знакомого лица в кадре
не доказывает личность говорящего; при нескольких людях неопределённость сохраняется.
Разрешения на действия хранятся отдельно от предположений о личности.

Приветствие запускается при подтверждённом приходе, один раз на посещение,
с общим cooldown между камерами. Не перебивает текущую речь и не повторяется
из-за поворота головы. Наблюдения и профили обрабатываются локально; в OpenAI
передаются нужные события и выбранные изображения для конкретного вопроса.

### Память и поведение

Разделить долговременные факты, историю выполненных действий и краткоживущее
состояние комнаты. Для каждого факта хранить источник, время, person_id и
возможность исправления/удаления. Текстовые embeddings могут помочь искать
память локально; они не заменяют отдельные embeddings лица и голоса.
SQLite достаточно для структурированного хранилища на первом этапе.

Переписать инструкции вокруг поведения: отвечать на языке собеседника,
быть кратким в командах и естественным в разговоре, помнить предпочтения,
не придумывать наблюдения и не объявлять выполнение до результата инструмента.
Текущую манеру дворецкого сделать необязательной настройкой.

## Порядок внедрения и проверка

1. Разделить конфигурацию провайдеров речи, рассуждений и зрения. Ключ OpenAI
   читать из окружения сервера; локальные модели оставить переключаемыми.
   Измерять конец пользовательской речи, первый tool call, эффект действия,
   первый воспроизведённый звук, ошибки и расход API.
2. Внедрить локальную речевую цепочку с текстовым OpenAI API: поток микрофона,
   инструменты, поток текста и озвучивание завершённых фраз по мере получения,
   перебивания, реконнект, отмена и обновлённый промпт.
   Проверить на реальном клиенте с телевизором и несколькими собеседниками.
3. Добавить прямые операции для частых сценариев и убрать лишние запросы
   к модели. Не ослаблять проверки разрешений ради скорости.
4. Добавить несколько камер, объединение присутствия и единые профили.
   Перенос существующих people.json/memory.jsonl выполнять с резервной копией.
5. Проверить длительную работу, отключение одной камеры, смену говорящего,
   приход двух людей, повторный вход, неизвестного посетителя, исправление имени,
   перебивание во время действия и отказ облачного API.

Цели для замеров, а не обещания: p50 первого звука после конца реплики ≤1.5 с,
p50 эффекта простой команды ≤2 с; p95 записывать отдельно и снижать по результатам.
Произвольная многошаговая работа в браузере не имеет гарантии в две секунды.
Успешность и отсутствие ошибочных действий проверять наряду со скоростью.

## Расходы и ещё неизвестные параметры

Лимит: $20 в месяц на API. Рабочий предел приложения предлагается $18,
остаток — запас, не бюджет для автоматического увеличения расходов.
GPT-Live/Realtime не входят в базовую схему. Электричество и оборудование
не включены в приведённые оценки API.

Проверенные текстовые тарифы за 1 млн токенов:

| Модель | Вход без кэша | Выход |
|---|---:|---:|
| GPT-5.4 mini | $0.75 | $4.50 |
| GPT-5.6 Luna | $0.20 | $1.20 |

Пример для mini без скидки за кэш: 3000 входных токенов и 300 выходных
оплачиваемых токенов на один API-запрос стоят $0.0036. За 30 дней:
50 запросов в день — $5.40; 100 — $10.80; 150 — $16.20.
Это API-запросы, не голосовые команды: одна команда с инструментами может
потребовать несколько запросов. Вход включает инструкции, схемы инструментов,
историю и результаты действий. Рассуждения, изображения и платные инструменты
тоже расходуют бюджет; пример не является прогнозом реального счёта.
Текущие длинные инструкции нужно сократить и подбирать только нужный контекст.

Перед отправкой каждого запроса резервировать верхнюю оценку стоимости
входа/выхода, сверять её с фактическим usage, учитывать параллельные запросы,
повторы и незавершённые вызовы, сохранять учёт между перезапусками. При
недостаточном остатке прекращать облачные вызовы; локальные команды остаются
доступными. При неизвестной стоимости не отправлять запрос автоматически.
Такой ограничитель покрывает только запросы этого приложения: желательно
использовать отдельный API-проект без других потребителей бюджета.

Ещё не установлены: количество/тип/разрешение камер, модель и расположение
микрофона, число и сложность запросов в день, доступные модели в API-аккаунте.
Итоговую смету проверить по usage в реальных тестах.
