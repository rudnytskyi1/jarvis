## 2. Что Jev умеет сегодня и что мы измеряем

Живая проверка 2026-09-22 (этот хаб, OpenRouter, `jev-latest`):

| Вопрос (`noul`/`choice`) | Ответ | Уверенность | Время |
|---|---|---|---|
| «Просят открыть веб-страницу?» ← «Rowan, open YouTube and search for MrBeast» | yes | 0.62 | 655 мс |
| «Просят открыть веб-страницу?» ← «what time is it» | no | 0.97 | 530 мс |
| «Какой инструмент нужен?» из `browser_control/pc_control/generate_image/none` | `browser_control` | 0.53 | 453 мс |
| «Просят изменить свет в комнате?» ← «turn the lights off please» | yes | 0.97 | 485 мс |

То есть System One отвечает за **полсекунды** и различает ровно те вопросы,
на которых большая модель тратит 4–8 с. Уверенность 0.5–0.6 у формально
верного ответа означает: порог «действовать автоматически» должен быть
настраиваемым, а решение с уверенностью ниже порога обязано **уходить большой
модели**, а не исполняться.

Сегодня Jev подключён узко: `server.decider.order` содержит четыре типа
(`route`, `model_level`, `addressed`, `hallucination`), и во всех стоит
`rules` первым, то есть Jev вызывается как запасной вариант.

## 3. Целевая схема: один batched-вызов Jev на реплику

System One принимает **несколько вопросов в одном запросе** (`questions:
{name: {...}}`) — это один HTTP-вызов и ~0.5–0.7 с на все вопросы сразу.
Значит, на каждую реплику делаем ОДИН вызов со следующими типизированными
вопросами:

| Имя | Тип | Вопрос | Куда идёт ответ |
|---|---|---|---|
| `act` | `noul` | «Просят что-то сделать с устройствами/ПК, или это разговор?» | Если `no` и уверенность ≥ порога — модель вызывается с пустым набором инструментов (быстрее, и она не «изобретает» действие). |
| `family` | `choice` | «Какое семейство инструментов нужно?» из `browser`, `pc`, `vision`, `media`, `memory`, `devices`, `telegram`, `people`, `none` | Модель получает **только это семейство** (10–28 инструментов → 3–6). |
| `followup` | `noul` | «Это продолжение предыдущей просьбы («ещё», «закрой это», «то же самое»)?» | Уточняет контекст хода, заменяет хрупкую регулярку `looks_like_followup`. |
| `hallucination` | `noul` | «Это осмысленная речь?» | Уже есть (D-03), переводится в тот же batched-вызов. |
| `addressed` | `noul` | «Обращаются к Rowan?» | Уже есть (D-02). |

Правила поведения (все — «не сломать работающее», ТЗ раздел 1):

1. **Fail-open.** Любая ошибка, таймаут (> 0.8 с), невалидный ответ или низкая
   уверенность — поведение ровно как сегодня (все инструменты, прежние
   эвристики). Jev никогда не блокирует ход.
2. **Никогда не исполняет.** Jev только сужает выбор; валидация аргументов и
   запуск остаются в `hub/tools.py` и `hub/llm.py` (`validate_args`, F-409).
3. **Кэш** (`server.decider.cache_ttl_s`, уже есть): та же реплика — 0 мс.
4. **Всё видно в панели**: каждый ответ Jev пишется в `decisions` и в
   `/admin/turns` рядом с моделью, так что «почему он так сделал» отвечается
   без логов (F-705).
5. **Порог уверенности** настраивается (`server.decider.understanding.
   min_confidence`, по умолчанию 0.65) — ниже порога сужение не применяется.

## 4. Задачи

### Фаза A — вернуть работоспособность (делается в этом заходе)

- **U-01 (сделано 22.09)** Снять отказы API: потолок расхода и обрезка
  контекста. Ссылка: DECISIONS.md API-01/API-02.
- **U-02** Адресная строка: не отказываться печатать URL, если UIA не
  подтвердил фокус; Ctrl+L и набор текста, а доказательство — реально
  загрузившаяся страница (как в `_navigate`). Плюс одна повторная попытка,
  если адресная строка не приняла текст. Тест: подставной UIA, который не
  сообщает о фокусе, — набор всё равно происходит.
- **U-03** Панель владельца: зафиксировать адрес, вход и разделы в
  `docs/ADMIN_PANEL.md` (Requests / Homes / Clients / People / Tracks /
  Audit), чтобы «где моя админка» больше не был вопросом.

### Фаза B — понимание через Jev (приоритет владельца)

- **U-10** `JevDecider.understand()`: один batched-запрос (`act`, `family`,
  `followup`) с общим таймаутом и разбором по именам вопросов.
- **U-11** `server.decider.understanding` в конфиге: `enabled`, `timeout_ms`,
  `min_confidence`, `families`.
- **U-12** `hub/tools.py`: карта «семейство → инструменты» (без пересечений,
  покрывающая все 28 инструментов — покрытие проверяется тестом).
- **U-13** `hub/llm.py`: `generate(..., tools=...)` и прокинутый список
  инструментов во все три транспорта (native, openai, responses).
- **U-14** `hub/app.py`: понимание считается один раз на реплику, до вызова
  модели; сужение применяется только при уверенности ≥ порога; результат
  пишется в `turn_trace` и в `decisions`.
- **U-15** Тесты: батч разбирается по именам; нет ключа/таймаут/битый ответ →
  полный набор инструментов; низкая уверенность → полный набор; высокое
  `family` → только это семейство.
- **U-16** Живой прогон: расширить `tests/live/scenarios.json` сценариями
  «одна реплика → правильное семейство» и прогнать с Jev и без него,
  сравнив успех и латентность.

### Фаза C — латентность (F-101, сейчас 8.5 с при бюджете 1.2 с)

- **U-20** Не пересчитывать STT 3–4 раза на одну реплику: отдавать
  диаризацию и STT параллельно и брать первый валидный результат.
- **U-21** Диаризация: убрать 0.7 с этапный дедлайн как отказ, оставить его

- **U-22** Кэш системного промпта: проверить, что стабильная часть промпта не
  меняется между ходами (иначе кэш OpenAI не работает и каждый ход дороже).

## 5. Риски и как мы их проверяем

| Риск | Проверка |
|---|---|
| Jev ответит неверно и сузит инструменты до ненужных | Порог уверенности + fail-open + тест U-15; в `decisions` видно каждый ответ |
| Плюс 0.5 с к каждой реплике | Кэш (TTL 60 с) + один batched-вызов вместо трёх + замер в U-16 |
| Текст уходит в облако | Только по флагу дома `cloud_decisions` (ТЗ 5.5, уже реализовано в `_privacy_context`) |
| Сузили инструменты и сломали редкий сценарий | `server.decider.understanding.enabled: false` возвращает всё как было |
